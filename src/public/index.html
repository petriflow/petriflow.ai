Petriflow MCP Server

Model Context Protocol server exposing Petriflow to AI tools

Streamable HTTP transport Apache-2.0 Cloud NAE packaging

About

This server implements the Model Context Protocol for Petriflow, letting MCP-compatible AI tools explore the Petriflow language (schema, elements, actions, components, examples) and validate processes over HTTP. The same server can build cloud NAE application package ZIPs. It's built with xmcp + Fastify.

Status: functional MCP server exposing the Petriflow tooling listed below, plus an HTTP application packaging API.

Connect from an AI tool

Claude Code (CLI)

Register the server with the Claude Code CLI:

claude mcp add --transport http petriflow http://localhost:3000/mcp
Claude Desktop

Add a custom connector in Settings → Connectors, or add this entry to your config file:

{
  "mcpServers": {
    "petriflow": {
      "url": "http://localhost:3000/mcp"
    }
  }
}
Cursor

Add to ~/.cursor/mcp.json (or your project's .cursor/mcp.json):

{
  "mcpServers": {
    "petriflow": {
      "url": "http://localhost:3000/mcp"
    }
  }
}
VS Code (MCP / Copilot Chat)

Add to .vscode/mcp.json in your workspace:

{
  "servers": {
    "petriflow": {
      "type": "http",
      "url": "http://localhost:3000/mcp"

  }
}

  "mcpServers": {

}
Other MCP clients

Any client that supports the MCP Streamable HTTP transport can connect directly to http://localhost:3000/mcp — no API key required by default.

Application packaging endpoints

Besides MCP, the server exposes an HTTP API that builds a cloud NAE application ZIP from Petriflow process XMLs. A package contains manifest.xml at the root and each process under processes/<appId>/<processId>.xml. A process XML must have its root <id> in the form <appId>/<processId>.

Method and path Purpose Request
POST /applications/package Build and return the application ZIP in one request. multipart/form-data with appId, name, and version (required), optional description, author, title, and validate=true, plus one or more process XML files. Uploading manifest.xml uses it verbatim instead of the metadata fields.
POST /applications/package/batches Start an in-memory packaging batch. Manifest fields or manifest.xml, plus optional validate=true. Returns batchId, processCount, validate, and expiresAt.
POST /applications/package/batches/{batchId}/processes Add one or more process XMLs to the batch. multipart/form-data with process XML files scoped to the batch application.
POST /applications/package/batches/{batchId}/complete Return the finished ZIP and delete the batch. No body.
DELETE /applications/package/batches/{batchId} Cancel the batch. No body.

A provided manifest.xml supplies app_id and the process list; its declared processes must match the uploaded set. Without a manifest, the manifest is generated from the metadata and process ids. With validate=true, processes are checked against the active Petriflow version in application context; invalid processes return 422 with issues and are not added. 

curl -X POST http://localhost:3000/applications/package \
  -F appId=my-app \
  -F name='My App' \
  -F version=1.0.0 \
  -F files=@processes/order.xml \
  -o my-app.zip

Incremental batch upload:

batch=$(curl -s -X POST http://localhost:3000/applications/package/batches \
  -F appId=my-app -F name='My App' -F version=1.0.0 -F validate=true)
id=$(echo "$batch" | jq -r .batchId)

curl -X POST "http://localhost:3000/applications/package/batches/$id/processes" \
  -F files=@processes/order.xml

curl -X POST "http://localhost:3000/applications/package/batches/$id/complete" \
  -o my-app.zip

Limits: 5 MiB per file, 100 files per request, 16 KiB per field, 100 processes and 50 MiB per application, 10 open batches, and 200 MiB retained. Batches expire after 30 minutes without an upload, are lost on restart, and are not shared between replicas. These endpoints are not authenticated; protect them at the ingress.
